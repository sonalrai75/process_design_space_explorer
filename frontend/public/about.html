1. Overview and objective

The Process Design Space Explorer is designed to move beyond static process maps and descriptive process-mining dashboards. It provides a quantitative process-engineering environment in which routing, staffing, automation, service times, rework, architecture choices, cost, capacity, cycle time, SLA performance, and stochastic robustness can be evaluated together.

The central design question is:

What process design or architecture provides the lowest cost while reliably meeting demand-satisfaction, cycle-time, SLA, and capacity requirements?

A process design is represented by a vector of design variables and, where relevant, a discrete architecture choice:

y = Fa(x)

where x contains design variables, a identifies an architecture family, and y contains resulting operational performance metrics.

2. Process model

The central object is a ProcessModel. It contains activities, resource pools, design variables, process architectures, demand, SLA parameters, cost information, and other operational characteristics.

Activities

Service-time behavior, names, resource-pool assignment, and process role.

Resources

Capacity, staffing levels, and cost structure.

Architectures

Alternative routing structures and process-family definitions.

Design variables

Fixed, continuous, quantized, and discrete variables.

A key schema detail is that workflow connectivity is architecture-specific:

model.architectures[i].transitions

Supported variable classes include:

  • Fixed — quantities held constant.
  • Continuous — e.g. automation or rework rates.
  • Quantized — e.g. integer staffing levels.
  • Discrete — e.g. architecture family.

4. Design-space optimization

The optimizer combines global feasibility exploration with local geometric optimization. Each architecture family is searched independently and then compared.

Coarse DOE search

Approximately 240 design points are evaluated per architecture to identify feasible regions, performance envelopes, low-cost seeds, and promising robust candidates.

Typical envelope outputs

  • Maximum throughput
  • Maximum demand satisfaction
  • Minimum P95 cycle time
  • Maximum SLA
  • Minimum maximum-resource utilization

This global stage is essential because SVD is local. It can describe nearby design geometry, but it cannot locate a distant feasible region by itself.

5. Evolving SVD and null-space optimization

Around a design point, a finite-difference Jacobian is constructed for the active process constraints or selected performance measures:

J = ∂g / ∂x

The Jacobian is decomposed using singular value decomposition:

J = UΣVᵀ

Small-singular-value directions identify combinations of design changes that have relatively little first-order effect on the active constraints. These directions form an approximate local null space.

Cost improvement in the null space

d = -N Nᵀ ∇C

The cost gradient is projected into the null space to identify a direction that can reduce cost while approximately preserving active process requirements. After each move, the process is resimulated, the active set may change, a new Jacobian is built, and SVD is recomputed.

This makes the method an evolving-SVD / evolving-null-space optimization, rather than a one-time decomposition.

Active constraints

Only binding or near-binding constraints are used to define the local design manifold. Constraints comfortably inside their allowable range do not unnecessarily restrict movement.

Quantized variables

Staffing and other integer-valued design variables are handled by projecting in continuous design space, snapping to permitted values, and then re-evaluating the resulting candidate.

6. Statistical robustness

A nominally feasible design may fail under different random arrivals or service-time realizations. The application therefore uses replicated discrete-event simulation to estimate design robustness.

Current robust constraints

Flow balance ≥ 98%
P95 cycle time ≤ 600 minutes
SLA ≥ 90%
Maximum resource utilization ≤ 95%

Flow balance

Absolute throughput was removed as a robustness constraint because a stable demand-limited process cannot sustainably produce more than its arrival demand. The normalized metric is:

Flow Balance = Throughput / Realized Arrival Rate

The user-facing metric is capped at 100%. It answers whether the system is keeping up with the demand actually realized in each replication.

Replication strategy

StageReplicationsCases per replication
Quick candidate screen12~500
Final validation40~1200

Candidate comparisons use common random numbers to reduce comparison noise. Final validation uses independent simulations and reports Wilson 95% confidence intervals.

Architecture ranking rule

  1. Architectures meeting the robustness target rank ahead of those that do not.
  2. Among target-meeting architectures, lowest annual cost ranks first.
  3. Robustness probability breaks remaining ties.
  4. If no architecture reaches target, highest robustness is preferred.

The target is:

P(all constraints satisfied) ≥ 90%

7. Event-log calibration

The application accepts CSV, XLSX, and XLS event logs and lets the user map:

  • Case ID
  • Activity
  • Start time
  • End time
  • Resource / performer

The calibration layer estimates:

Activities
Discovered from unique event names.
Service times
Estimated from timestamps.
Routing probabilities
Estimated from directly-following transitions.
Rework
Detected through repeated/backward transitions.
Arrival rate
Estimated from case-start timestamps.
Resources
Observed performers and approximate capacity.

Routing probabilities are estimated as:

P(B|A) = N(A→B) / Σⱼ N(A→j)

The calibrated result becomes the active process model used by both simulation and robust optimization.

8. Visual Process Modeler

The current modeler supports general directed workflows rather than only linear processes. Connectivity is read from the active architecture's transition graph.

Supported workflow structures include:

  • Branching
  • Merging
  • Exception paths
  • Rework loops
  • Multiple terminal routes
  • Routing probabilities

Users can currently edit:

  • Activity names
  • Mean service times
  • Resource-pool assignments
  • Transition source, target, and probability
  • Resource capacities
  • Add/remove activities
  • Add/remove transitions
  • Download the active model as JSON

10. Current limitations

  • Resource groups are inferred heuristically from event-log performer labels; users should review/edit inferred pools when source systems do not provide an explicit resource-group field.
  • Architecture generation is primarily predefined rather than automatically invented.
  • XES import is not yet implemented.
  • Process discovery is currently lightweight rather than a full PM4Py/Petri-net/conformance stack.
  • Full shift calendars, holidays, and time-varying resource schedules are not yet generalized.
  • Batching and advanced queue disciplines are not yet generalized.
  • The visual modeler is graph-based rather than a complete BPMN editor.
  • Forty final robustness replications are appropriate for an interactive prototype but not for very tight statistical guarantees.

12. Recommended next stage

The next major technical step is to make resources and workflow semantics fully generic. The current optimizer still contains some design-variable assumptions originating in the original demonstration process.

A fully generic formulation would automatically create resource-capacity variables from an uploaded event log, allowing arbitrary resource groups such as underwriters, claims adjusters, controllers, robotic automation, external vendors, or operations teams.

Concise technical description

Process Design Space Explorer is a process digital-twin and design-optimization platform that combines event-log calibration, discrete-event simulation, process mining, architecture-family search, evolving-SVD/null-space design optimization, and replicated stochastic robustness analysis. It converts operational process data into an editable simulation model and searches for low-cost process designs that reliably satisfy cycle-time, SLA, demand-satisfaction, and capacity constraints.
